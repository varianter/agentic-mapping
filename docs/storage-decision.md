# Storage and access decision

Design and implementation, 2026-11-04. Human review requested actual persistent storage in this PR. The app now uses the existing Bun/Hono runtime with file-backed SQLite, a single admin key (`ADMIN_KEY`) and no per-sheet owner. Workers/D1 remains an alternative if the owner chooses managed hosting. Participant completion links now follow the approved defaults documented in [the implementation map](participant-access.md).

## Implemented behavior

- [`server.ts`](../server.ts) configures [`server/app.ts`](../server/app.ts): durable SQLite, [HTTP Basic authentication](https://hono.dev/docs/middleware/builtin/basic-auth) that compares the password to `ADMIN_KEY` in constant time, revision checks and an explicit public-file allowlist. Storage later moved to Upstash Redis (#16); set the KV variables and `APP_ORIGIN` behind HTTPS; see [setup and operations](../README.md).
- [`client/db.js`](../client/db.js) uses the same-origin API. [`client/app.js`](../client/app.js) serializes saves, preserves newer edits during requests, reports failures and conflicts, warns on unsaved navigation and offers retry, draft download and explicit reload. Unknown IDs never fall back to another interview. Lists contain all sheets; there is one admin and no owner.
- [`index.html`](../index.html) retains the complete interviewer form. The username is ignored and sheets have no owner; the editable interviewer field is just form data. Interviewer authentication is challenged by the browser before loading the app; closing the browser session clears its cached Basic credentials. `/participant` has a separate entrypoint and scoped bearer API, without interviewer authentication or list loading.
- [`legacy.html`](../legacy.html) and [`client/legacy.js`](../client/legacy.js) export existing IndexedDB notes only on request, without removing originals. JSON import explicitly uploads with the admin key, preserves IDs/timestamps and rejects collisions; identical retries do not duplicate notes. No automatic upload occurs.
- [`.github/workflows/pages.yml`](../.github/workflows/pages.yml) now publishes only the old-origin exporter. The full app requires Bun hosting; Pages cannot run its API. IndexedDB follows the [same-origin policy](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), so each old browser/device must export before migrating origins.
- The SQLite backup script was removed in #16 when storage moved to Upstash Redis. [`tests/storage.test.ts`](../tests/storage.test.ts) verifies reopen, admin-key rejection, conflicting revisions, imports and public-file rejection; browser checks cover the user flows.

The remaining sections distinguish the implemented interviewer baseline from the participant contract and production operational responsibilities. No external host or credentials are provisioned by this change.

### Cost assumptions

Planning workload: 20 interviews/day, 600 debounced saves/interview, fewer than 10,000 indexed row reads/day and less than 100 MB including indexes. This means 12,000 save requests/day before retries and identity traffic; measure actual database rows written, including index maintenance. The implemented baseline refreshes the list after saves; revisit this at higher usage to avoid repeated scans.

| Option | Budget basis and limits |
| --- | --- |
| Bun/Hono + SQLite | No separate database service bill. Monthly total is host + durable disk + encrypted off-host backups + domain/identity costs + operator time. No host has been selected, so there is no verified monthly quote; an existing maintained host may reduce incremental cash cost. |
| Workers + D1 Free | Under these assumptions, potentially $0 for compute/database, excluding domain, identity and external backups. [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/). |
| Workers + D1 Paid | Workers starts at $5/account/month with 10 million dynamic requests and 30 million CPU ms/month; excess costs $0.30/million requests and $0.02/million CPU ms. Free quota exhaustion is a save failure, not a reason to claim success locally. Benchmark the authenticated save path against CPU limits, enable usage alerts and revisit the budget before rollout. A free tier does not remove the need for an operational owner.

## Access model and participant contract

Admin-key and participant operations below are implemented. One admin key gates all interview management; sheets have no owner. Each list, read, update, delete, export and link-management route must require the admin key. Parameterize SQL and validate fields and request sizes server-side.

Participant access is a separate, narrow API. A server-generated, high-entropy bearer token grants access to exactly one sheet and explicit read/write field allowlists; store only its hash, sheet binding, expiry and revocation state. Check them on every read and write, including requests from previously opened tabs. Reject extra/private fields rather than silently accepting them. The approved allowlist is all 27 grid fields plus `good`, `surprised`, `missing`, `advice`; links expire after seven days and only the admin can issue, replace or revoke them.

| Operation | Anonymous visitor (no valid link) | Authenticated interviewer | Valid participant-link holder |
| --- | --- | --- | --- |
| Load app shell / guide | Participant shell/assets are public without data; interviewer shell/guide require sign-in. | Allow. | Separate participant entrypoint; no interviewer list or controls. |
| Create / import sheet | Deny, require sign-in. | Allow. | Deny. |
| List sheets | Deny. | All sheets and their summaries. | Deny; no sidebar data or other-sheet counts. |
| Read / print / export sheet | Deny. | Allow. | Only linked sheet's approved visible fields; print/export must use the same projection. |
| Update sheet | Deny. | Allow with matching revision. | Only linked sheet's approved editable fields with matching revision. |
| Delete sheet | Deny. | Allow. | Deny. |
| Issue / revoke / rotate participant link | Deny. | Allow. | Deny; cannot extend expiry or issue another link. |
| Read database, backups or deployment credentials | Deny. | Deny through the app, even with the admin key. | Deny. |

### Rejection and exposure scenarios

- A visitor guesses a sheet UUID: require interviewer authentication or a valid participant capability; do not return notes, names or summaries. A request without the admin key gets `401` on every interview and link route.
- A participant changes the sheet ID in a request: resolve the sheet from the token binding; reject mismatched IDs with a generic `404`. Never fall back to another interview, even though the admin could access it.
- A missing, malformed, expired, revoked or rotated token gets a generic unavailable-link response, no interview fields and no fallback. Rate-limit invalid attempts. A revoked open tab cannot read or save again; hide the form on rejection and allow an unsaved draft download, though already copied notes cannot be recalled.
- A valid link is forwarded or leaked: anyone holding it has the same access until expiry/revocation. Link-only access cannot prove the interviewee's identity. Link-only possession was accepted in issue #6; participant sign-in is out of scope.
- Keep raw tokens out of query strings, server logs, analytics, error reports and persistent browser storage. The approved handoff keeps the token in the delivery fragment for page reloads and authenticates API requests with an Authorization header, without cookies or browser storage. Check the backing link on every read/save; see the README for browser history/clipboard handling. Use `Referrer-Policy: no-referrer` and no third-party scripts on the participant page.
- Hide create/list/delete controls in participant mode, but enforce every permission on the server. Use CSRF protection and Origin checks for cookie-authenticated mutations; CORS and hidden buttons are not authorization. Return interview responses with `Cache-Control: no-store`; do not share-cache them or log request bodies.
- Requests for `.sqlite`, `-wal`, `-shm`, SQL exports, `.env` or repository configuration must return no files. Package only public assets, keep Bun database/backups outside that directory, and keep D1 access in Worker bindings. Deployment/identity secrets belong in host secret storage, never browser modules or `_site`. If credentials leak, rotate them and invalidate affected sessions/links; removing a public file alone is insufficient.

## Preservation, saves and rollout

### Preserve existing browser data

1. Before moving origins, release an export path on the old Pages origin that reads the existing IndexedDB schema and downloads a JSON array containing every sheet, field and timestamp. Keep legacy unprefixed grid fields; `fillForm` currently maps them to Individual. PDF is useful for reference but cannot restore structured data.
2. Keep the old origin available as a local-data recovery/export page through an agreed migration window. Each browser profile/device containing notes needs its own export. Do not clear IndexedDB or redirect users away before they can export; a new host cannot retrieve it. Do not silently upload existing interview notes.
3. After sign-in on the new host, choose Import JSON to explicitly upload with the admin key. Validate field types and request size; preserve IDs/timestamps and add server revision metadata. Reject colliding IDs without overwriting data and accept only identical create/import retries. Partial failures report the imported count; the original export remains the recovery copy. An import preview and collision-remapping UI may follow later.
4. Compare imported counts and representative full sheets, including legacy grids, then export/download a recovery copy. Keep the original IndexedDB/export until the owner confirms migration and retention requirements. If JSON export fails, show the error and leave local data intact; the recovery page does not claim migration succeeded.

### Save and overlap contract

- Store server-managed integer `revision` and timestamps alongside the existing field shape. Updates and deletes use an atomic revision check, incrementing the revision on success. Participant writes patch only allowed fields; sending a whole form must not blank hidden notes.
- Serialize saves per sheet in the client and capture the sheet ID, payload and base revision per request. Keep newer edits dirty while an older request completes; only acknowledge the submitted snapshot, never mark subsequent typing saved. Navigation must not apply an old response to a different sheet.
- A stale revision returns `409 Conflict` without overwriting data. Stop automatic retries and retain the in-memory draft. The user downloads JSON before explicitly reloading and manually merging against the new revision; no automatic merge UI is implemented. Apply this to two tabs, two devices and interviewer/participant overlap. Do not use client clocks or silent last-write-wins.
- Network loss, timeout, quota, disk-full or server errors leave a visible unsaved state and a retry/export option. The implemented baseline retains the draft in memory, warns on page leave and offers immediate JSON download; it does not persist local drafts. Never show server success before commit acknowledgment. Durable local recovery and participant draft retention require a separate shared-device policy.
- On an ambiguous failed update, a retry uses the same revision; if the earlier write committed, the retry conflicts and the user must download/reload and compare. Create/import retries compare the same ID and full payload to avoid duplication. On `401`, retain the draft and require reauthentication; on `403`/unavailable link, stop retries and require renewed access. A delete must not be undone by a delayed save; updates never upsert missing sheets.
- `pagehide`/visibility events cannot guarantee a completed network save. Show pending changes, attempt ordinary saves early, warn before navigating with unsaved work and retain recovery options; background sync is not a prerequisite for slice 2.

### Deployment transition and recovery

- Hosting and data updates are separate: Pages publishes only the exporter; interviewers open the full app at the separately deployed Bun origin. Browser create/import, autosave and delete requests go to that origin's authenticated `/api/sheets` API, which commits to the configured store. Pages never forwards these writes, and its workflow does not deploy Bun or change the database. The host operator deploys code separately while preserving the durable database; ordinary saves need no deployment. See the [hosting and save flow](../README.md#github-pages-and-the-storage-host).
- Prefer serving public assets and `/api/*` from one HTTPS origin for either option. The Pages job now publishes the old-origin exporter; deploy the Bun application separately using the README instructions. Retaining Pages plus a separate API is possible but adds credential/CORS configuration and is not the recommended first slice.
- Bun: root static serving is replaced with an exact public-file allowlist and the initial schema is created on startup. Configure an absolute durable database path, supervision, TLS and backup jobs; future schema changes require explicit migrations. Workers: add a Worker entrypoint, Wrangler assets/D1 configuration and separate staging/production bindings; route `/api/*` through the Worker before asset handling, with API errors never rewritten to `index.html`. Only public assets go in the upload directory. [Routing documentation](https://developers.cloudflare.com/workers/static-assets/).
- Keep relative asset links working when moving from `/agentic-mapping/` to the new origin. Update local scripts, deployment credentials and README only in the selected implementation slice; do not introduce a frontend build requirement.
- Before enabling remote writes, test persistence after restart/redeploy and restore a backup into isolated staging. Proposed baseline: daily encrypted external backups, 30-day retention, at most 24 hours of data loss and restoration within one working day; the owner must accept or revise these targets and retention rules.
- Use additive migrations and a backup before schema changes. On a bad release, disable writes, preserve the database/drafts and roll back to compatible code or restore in staging first. Do not revert to independent browser-only writes as a silent fallback. A database restore may resurrect revoked links: invalidate participant sessions/links before reopening access.

## Conditional recommendation and implementation slices

**Prefer Workers static assets + D1 if the owner accepts Cloudflare hosting, its costs/data handling and an interviewer identity provider.** With small-scale usage and minimal ongoing maintenance as the priority, managed persistence and recovery outweigh the extra platform resource. Choose Bun/Hono + SQLite instead if an existing durable host has a named operator who accepts patching, backups and restore duties, or hosting requirements rule out Cloudflare. The implemented baseline uses Bun/SQLite to deliver persistence with the existing runtime now; production hosting still needs a named operator. The original conditional preference remains useful if managed hosting is selected later. Admin-key authorization is enforced by the new API, rather than by the hosting platform.

### Remaining deployment and participant decisions

- **Hosting and operations:** confirm that setup/maintenance outweigh large-scale needs; name a Bun host/operator for this implementation (or plan a later Cloudflare migration), account/billing owner, data-location requirements, budget, retention and recovery targets.
- **Interviewer identity (decided, #15):** one secret `ADMIN_KEY` (at least 32 characters) sent as the Basic password gates all interview management; there are no named accounts or per-sheet owners. Old local SQLite data is not migrated; delete it. Key rotation and multiple admins are out of scope.
- **Visible/editable fields (decided):** the 27 grid fields and four approved reflections are participant-readable/editable; identity, context, discipline, contacts and all other fields remain private.
- **Link-only access (decided):** possession grants access for seven days; the admin can replace/revoke access. Drafts remain in memory with explicit download. Validate the completion window in a real handoff trial.
- **Existing notes:** approve uploading local interview data, the old-origin export window and how long local exports and backups may retain it. Existing browser notes remain untouched until explicitly imported; the app has no browser-only save fallback.
